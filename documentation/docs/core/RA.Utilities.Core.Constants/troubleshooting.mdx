# Troubleshooting & FAQ

## Common Issues

### My `ResponseType` is serializing as a number instead of a string

**Cause**: Without a converter, `System.Text.Json` serializes enums as numbers (`11` instead of `"Error"`).

**Fix**: The `[JsonConverter(typeof(ResponseTypeJsonConverter))]` attribute is built into the package and applied automatically. If you see numeric output, ensure you're using `System.Text.Json` with default options, and that your custom `JsonSerializerOptions` don't override the attribute-level converter. The converter serializes to plain strings (e.g., `"NotFound"`).

### Can I use `ResponseType` in a `switch` expression?

**Yes — fully.** `ResponseType` is a standard `enum`, so constant patterns work and the compiler can verify exhaustiveness:

```csharp
// ✅ Constant patterns (preferred)
var label = responseType switch
{
    ResponseType.Success => "OK",
    ResponseType.NotFound => "Not Found",
    ResponseType.Conflict => "Conflict",
    ResponseType.BadRequest => "Bad Request",
    ResponseType.Unauthorized => "Unauthorized",
    _ => "Other"
};
```

### How do I compare two `ResponseType` values?

Use `==` or `.Equals()` — enum members are singletons, so comparison is simple and allocation-free:

```csharp
ResponseType a = ResponseType.NotFound;
ResponseType b = ResponseType.NotFound;

bool same = a == b;       // true
bool sameEq = a.Equals(b); // true
```

### Can I create a `ResponseType` from a string at runtime?

Yes, with the standard `System.Enum` APIs:

```csharp
// ✅ Parse a member name
ResponseType type = Enum.Parse<ResponseType>("NotFound", ignoreCase: true);

// ✅ Safer for untrusted input — numeric strings parse to undefined values
if (Enum.TryParse(value, ignoreCase: true, out ResponseType parsed) && Enum.IsDefined(parsed))
{
    // safe to use parsed
}
```

Note: the JSON converter (`ResponseTypeJsonConverter`) is more lenient than `Enum.Parse` — it matches case-insensitively and falls back to `ResponseType.Error` for `null`, empty, whitespace, or unknown strings instead of throwing.

### `BaseResponseCode.Created` doesn't exist — what should I use?

`Created = 201` was intentionally omitted from `BaseResponseCode` because the package focuses on response codes commonly used in _error_ and _generic success_ scenarios. For a `201 Created` response, use the ASP.NET Core built-in helper:

```csharp
return CreatedAtAction(nameof(GetProduct), new { id = product.Id }, product);
```

If you need the integer constant, define it in your own project or use `201` directly.

## Known Limitations

- **Closed set of values**: Consuming projects cannot add new `ResponseType` members. For an outcome without a dedicated member (e.g., `PaymentRequired`), use the closest built-in member (typically `Error` or `Problem`) and communicate the specifics through the error code and message.
- **Lenient deserialization**: Unknown JSON strings silently fall back to `ResponseType.Error` rather than throwing. Validate early if you need to distinguish "unknown type" from a genuine error.
- **`default` is `Success`**: `default(ResponseType)` and uninitialized fields are `ResponseType.Success` (value `0`). Use explicit members in models where `Success` is not the right default.
- **No implicit conversion from `string`**: Use `Enum.TryParse`/`Enum.Parse` or the built-in members directly.
- **No localization support**: `BaseResponseMessages` provides English-only strings. For multi-language support, use these as fallback defaults and implement your own localization layer.

---

## Performance Tips

- **Enum members are singletons**: `ResponseType.NotFound` involves no allocation — member access is as cheap as an enum gets.
- **Prefer `TryParse` over `Parse`**: When the input may be invalid, `Enum.TryParse` avoids exception overhead on the failure path.
- **Constants are inlined**: `BaseResponseCode` and `BaseResponseMessages` use `const`, so the values are inlined at compile time with zero runtime cost.
